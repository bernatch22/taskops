taskops v2 · propuesta de rediseño · 2026-07-28 · leído el código entero antes de escribir esto

Un CLI para el dev.
Tools para los agentes.
Reportes que se escriben solos.

El problema de hoy no es lo que taskops hace — es que muestra las tres audiencias mezcladas. taskops --help lista 19 comandos y 12 son cableado que ningún humano tipea jamás. Esta es la separación completa, comando por comando, con la migración exacta.

0 · El diagnóstico: 19 comandos, 3 audiencias, 1 help

Cada comando actual, clasificado por quién lo invoca de verdad:

# EL DEV tipea (7):
init · studio · report · log · sync · recover · plan

# EL AGENTE llama — pero por MCP, no por CLI (5):
next · update · ask · dispatch · (plan otra vez)

# LOS HOOKS invocan — nadie los tipea NUNCA (7):
guard · hook · ingest · brief · inbox · track · checkout

Los 5 del medio son duplicados del MCP: el agente ya los tiene como tools con mejor contrato. Los 7 de abajo son protocolo — hook lee JSON de stdin, guard contesta con exit code 2, track imprime nada a propósito. Un dev que abre el help no puede saber cuáles son para él, y eso es exactamente lo que hace que el sistema se sienta complejo aunque el motor sea simple.

1 · studio → taskops ui

"Studio" promete un lugar donde se crea algo (visual studio, recording studio). Lo que este comando hace es mostrar: el board vivo, la actividad, los reportes. El nombre correcto es el más aburrido: 

taskops ui                    # → http://127.0.0.1:2140/
taskops ui --readonly --host 0.0.0.0 --token …
  • por qué "ui" y no "board" — board es UNA vista de las tres (Board · Activity · Reports). El comando levanta la interfaz entera.
  • migración — studio queda como alias oculto una versión, con una línea deprecation en stderr. Cero scripts rotos.
  • El directorio studio/ del repo pasa a ui/ en el mismo commit, para que el nombre no viva a medias.

2 · El CLI del developer — 7 comandos, y se entiende en una pantalla

taskops init                  preparar el repo (hooks, log, guía)
taskops ui                    la interfaz web en vivo
taskops tasks …              ver y tocar las cards        ← nuevo dominio
taskops report …             board · standup · day        ← + el diario
taskops run [n|ids]           correr cards con Claude       ← experimento
taskops recover               soltar cards de workers muertos
taskops sync                  reconciliar con el log commiteado

2a · taskops tasks — el dominio que faltaba

Hoy para ver la lista hay que pedir un "reporte" (report board), y para cerrar una card hay que saber la sintaxis de update --status done --comment …. Eso es pensar como el motor, no como el dev. El dominio explícito: 

taskops tasks                  # la lista, compacta: id · estado · título · quién
taskops tasks show tk-4f2a     # una card entera (hoy: ask)
taskops tasks add "título" [--spec …] [--after tk-x]   # UNA card sin escribir JSON
taskops tasks done tk-4f2a -m "qué pasó"               # cerrar
taskops tasks release tk-4f2a -m "hasta dónde llegué"  # devolver a la cola
taskops tasks edit tk-4f2a --spec … --title …          ← hueco real de hoy: no existe
taskops tasks log tk-4f2a      # la conversación del agente (hoy: log)
taskops tasks search "texto"
  • reusa todo — cada subcomando es el mismo usecase que ya existe (ask, update, search, session_log). Es un re-agrupado de la superficie, no lógica nueva. add llama a plan con una lista de uno.
  • edit no existe hoy — está anotado como "hueco real" en docs/flujos.html. Entra acá: un evento edited nuevo + replay, mismo patrón que todo lo demás.
  • plan JSON sigue — taskops tasks plan archivo.json para el batch con deps; el caso de a una deja de exigir JSON.

3 · Las tools del agente — 7, con dos limpiezas

La superficie MCP está bien dimensionada y no se toca en forma: cada tool nueva le cuesta contexto a toda sesión conectada. Los cambios son de contenido:

toolcambio
taskops_nextigual — claim atómico + spec + inbox + colisiones
taskops_updateigual — status, comment, mentions, blocked_on, no_code
taskops_askigual — una card o búsqueda
taskops_planigual — el batch con deps
taskops_dispatchigual — briefs, nunca spawn (la regla anti-billing queda)
taskops_recoverigual
taskops_reportsacar fleet y burndown del enum (uno lo matamos, el otro contesta "not implemented" desde 0.1.0) · sumar day — el reporte diario de §4. Así el agente contesta "¿qué se hizo ayer?" con UNA llamada.

Esta es la simetría completa del sistema: el dev tiene 7 comandos, el agente tiene 7 tools, y los dos hablan con los mismos usecases — que es la invariante de arquitectura que ya está testeada.

4 · Reportes diarios — más que un LLM: el dossier del día

Lo que pedís no es un standup: es el dossier — todo lo que pasó un día, agrupado, con files, commits y diffs, linkeado. Eso se construye en dos capas, y la separación es el diseño entero:

Capa 1 — el dossier determinista (sin LLM, siempre disponible)

taskops report day                    # hoy
taskops report day --date yesterday   # o 2026-07-27

Una proyección más sobre events.jsonl + git — cero storage nuevo. Por día, cortado en medianoche de calendario:

# 2026-07-27 — 6 cards cerradas · 3 en vuelo · 14 commits · 4 actores

## Cerrado
✓ tk-8c82bf — El peaje de episodios (agent:me/toll1, 2.1h de claim a done)
    ◆ a3f2c1d feat: leave-one-out episode toll
      src/axion/research/episode_toll.py (+214 −12) · tests/… (+89)
      └─ diff: taskops tasks show tk-8c82bf · git show a3f2c1d
    💬 3 comments — el último: "el N del DSR quedó en 47"

## En vuelo / bloqueado  (qué quedó abierto y por qué)
## Conversaciones        (mentions y handoffs del día, con quién)
## Por actor             (el roll-up que ya existe en Activity)
  • los diffs — el evento commit ya carga sha, subject y files. Las stats (+214 −12) salen de UN git diff-tree --numstat batcheado, el mismo patrón que branch_states usa hoy: un subprocess por reporte, no por commit. El diff completo no se copia — el reporte lo linkea (git show sha / la card en el ui), porque el log commiteado tiene que seguir siendo legible por un humano.
  • reproducible — mismo día, mismo log → mismo reporte. Es lo que el agente lee con taskops_report day, y es el INPUT de la capa 2.

Capa 2 — la narración, escrita por Claude, guardada inmutable

/taskops:digest              # skill del plugin: la sesión que YA tenés genera y commitea
taskops report day --write   # guarda el dossier + narración en .taskops/reports/2026-07-27.md
  • quién llama al modelo — la sesión de Claude Code que ya está corriendo, vía un skill. Cero dependencia nueva en el engine, cero API key, usa la suscripción pagada — el mismo argumento por el que taskops_dispatch se niega a spawnear sesiones facturadas. (Opcional después: taskops[llm] con el SDK para el caso cron sin sesión.)
  • se guarda, nunca se regenera al leer — un reporte que dice algo distinto cada vez que lo abrís no es un reporte. .taskops/reports/YYYY-MM-DD.md va commiteado con el log: el que hace git pull se lleva la historia narrada.
  • fingerprint — cada reporte guarda hasta qué evento cubrió (max_seq). Si después llegan eventos de ese día, el ui muestra "desactualizado, faltan 12 eventos" en vez de mentir. Stale visible > stale silencioso.

La vista Reports en el ui

Tercera pestaña: Board · Activity · Reports. Una lista de días; cada día muestra SIEMPRE el dossier de capa 1 (existe aunque nadie generó prosa), la narración si está escrita, links a cards y commits, y el aviso de stale. Reusa /api/activity + un /api/report?date= nuevo.

5 · taskops run — Claude como proceso, el experimento honesto

Hoy esto existe escondido como dispatch --spawn, y funciona: worktree por card, claude -p headless con allowlist de tools, identidad inyectada, lease que expira si muere. Lo que le falta es un nombre honesto y la advertencia en la puerta: 

taskops run                    # las mejores 3 ready, un proceso Claude cada una
taskops run tk-4f2a tk-8b31    # estas dos
taskops run 5 --model claude-haiku-4-5   # cards mecánicas, modelo barato
⚠ cada worker es una sesión facturada nueva — para paralelizar gratis,
  dispatchá sub-agentes desde una sesión (taskops_dispatch)
  • desde el ui también — un botón "run" en una card ready que llama al mismo usecase. Deshabilitado en --readonly, y con la misma advertencia de billing antes de confirmar. Es el "correr tareas desde el ui" que pediste, sobre mecánica que ya está testeada.
  • sigue marcado experimento — en el help y en el README. La vía recomendada para fleets sigue siendo dispatch + sub-agentes.

No se toca: el motor (leases, state machine, replay, sync), las 7 tools en forma, el event log y su formato, los hooks instalados. Todo esto es superficie — que es exactamente lo que la arquitectura de capas compró: los transports son delgados, así que reordenarlos no puede romper una regla.
