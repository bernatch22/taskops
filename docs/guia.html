La guía completa

El sustrato de coordinación que a Claude Code le falta: tareas persistentes con un grafo de dependencias, claims atómicos que sobreviven a un agente muerto, cada commit atado a la tarea que lo motivó, y agentes que se hablan entre developers y entre máquinas. Cero dependencias, un SQLite por repo, un log de eventos commiteado, ningún servidor.

Flow 1 — el ciclo de vida de una card

Todo es una card con ocho estados posibles. La máquina de estados vive en un solo lugar (engine/machine.py) y el server rechaza cualquier movimiento ilegal con un mensaje que nombra los movimientos legales. 

              taskops_plan                    taskops_next
                   │                        (claim atómico)
                   ▼                              │
   · backlog ──────────▶ ○ ready ────────────────▶ ◐ claimed
       ▲   deps abiertas    ▲                        │  │
       │                    │ lease vence            │  └────────────┐
       │                    │ o "released"           ▼               ▼
       │                    └──────────────── ● in_progress ──▶ ◆ review
       │                                          │  │              │

       │            ✕ blocked ◀───────────────────┘  │ eval ok      │
       │            (espera humano                   ▼              ▼
       │             o dependencia)              ✓ done ◀───────────┘
       │                 │                           │
       └─────────────────┘                    done desbloquea a
                                              quien esperaba — solo,
   — cancelled: legal desde cualquier         sin polling
     estado abierto, sin guard (no hay
     trabajo que mostrar, a propósito)

   done es TERMINAL: reabrir haría que el log diga que una tarea
   terminó dos veces. Lo honesto es una tarea nueva que referencia la vieja.

Y así se ve una card cuando el agente la reclama — el orden es el diseño, porque un agente lee de arriba a abajo y puede parar antes:

Flow 2 — ¿qué pasa si un agente quiere una card que depende de otra?

No puede. Ni por accidente ni pidiéndola por id — ese segundo camino era un bug real, cazado siguiendo la guía de uso, y hoy está pineado por un test. La respuesta nombra al blocker, porque el movimiento útil casi siempre es ir a trabajar en él. 

   ana planeó:   [0] "Plan the API"  ◀─── after: [0] ─── [1] "Implement handlers"

   AGENTE DE BERNA                              TASKOPS
   ─────────────                                ───────
   taskops_next task=tk-d7de92  ──────▶  la task está en backlog con deps abiertas
        (la bloqueada, por id)                  │
                                                ▼
   ◀──────────────────────────────  # nothing to claim
                                    tk-d7de92 is waiting on tk-fca539 — finish
                                    those first, or claim one of them
                                                │
   taskops_next  ─────────────────▶  el scheduler le da tk-fca539 (la ready)
   ... trabaja, commitea ...                    │
   taskops_update status=done  ───▶  cierra ────┤
                                                ▼
                                    Unblocked 1 task(s):
                                    - tk-d7de92 — Implement handlers
                                                │
   taskops_next  ─────────────────▶  ahora sí: tk-d7de92 es suya

   nada poletea: el desbloqueo pasa EN el write que cierra la dependencia,
   y update te dice qué acabás de liberar para la flota

El scheduler además ordena por prioridad y castiga colisiones: una task cuyos files se solapan con lo que un agente vivo está editando se va al fondo de la cola, por encima de cualquier urgencia — dos agentes en un archivo son dos agentes a punto de deshacerse mutuamente.

Flow 3 — cómo se comunican los agentes

No hay una sexta tool de chat, a propósito: un mensaje sobre una tarea vive en el hilo de esa tarea, donde se puede encontrar en tres semanas. Mandar es update con mentions; recibir no es una tool — el inbox llega solo, por hooks. 

   AGENTE DE ANA                    TASKOPS                    AGENTE DE BERNA
   ────────────                     ───────                    ───────────────
   taskops_update                      │                             │
     task=tk-8b31d0                    │                             │  (está trabajando,
     comment="Estoy reescribiendo      │                             │   corre tools)
       token.py — esperá a que         │                             │
       lo suba."                       ▼                             │
     mentions="agent:berna/w1"   Event(kind=message) ──▶ SQLite      │
                                       │                             │
                                       │         PostToolUse hook ◀──┤ su SIGUIENTE
                                       │         `taskops inbox`     │ tool call
                                       │               │             │
                                       ▼               ▼             │
                                 studio lo ve     📬 1 message(s):   │
                                 EN VIVO (SSE)    agent:ana/api-1 on │
                                                  tk-8b31d0: "Estoy  ├──▶ lo LEE inyectado
                                                  reescribiendo..."  │    en su contexto
                                                                     │
   la entrega se marca por (actor, evento) — nunca por cursor de tiempo,
   porque los hooks disparan en un orden que nadie controla y un cursor
   saltearía el mensaje que llegó tarde. leído una vez = entregado.

   PUNTOS DE ENTREGA (Claude Code no acepta push a mitad de turno):
     SessionStart  → brief: tus tasks + tus mensajes, al arrancar
     PostToolUse   → inbox: lo nuevo, en tu siguiente tool call (segundos)
     taskops_next  → el inbox viaja con el claim
     Stop          → checkout: tu resumen queda en el hilo (standup gratis)

Los humanos usan exactamente el mismo canal: el compose del studio postea un comment con mentions, y le llega al agente igual que un mensaje de otro agente. No hay un mecanismo aparte para personas.

Flow 4 — cada commit atado a su tarea, por la fuerza

   el agente tipea:  git commit -m "Add the token table"
        │
        ▼
   PreToolUse hook (matcher: Bash) ──▶ taskops hook pre-tool-use
        │
        ├── no es un commit ─────────────▶ silencio, pasa directo (gratis)
        │
        ├── branch tk/<id>/... + lease vivo
        │        │
        │        ▼
        │   REESCRIBE el comando del agente (updatedInput):
        │   git commit -m 'Add the token table
        │
        │   Task: tk-4f2a9c'          ◀── el agente nunca escribe el trailer
        │                                 ni ve un error por él
        │
        └── sin claim / branch ajena ────▶ DENY, y el agente lee:
              "taskops: agent:ana/w2 holds no live lease on tk-4f2a9c.
               Claim it (taskops_next task=tk-4f2a9c) before committing"
        │
        ▼
   post-commit hook (git) ──▶ taskops ingest commit HEAD
        │                     registra el sha contra la task — TAMBIÉN los
        │                     commits que el guard nunca vio: un commit a mano
        ▼                     en terminal, un --no-verify, un rebase
   taskops_update status=done
        │
        └── guard: ¿hay commit atado? NO → rechazado.
            "tk-4f2a9c has no commit bound to it..."
            (con no_code + justificación escrita, para research/decisiones)

   por qué DOS mecanismos: la branch se puede chequear ANTES de que el commit
   exista; el trailer sobrevive al squash y al rebase, que es como muere
   toda branch. el guard falla ABIERTO: si taskops se rompe, tu commit sale.

Flow 5 — las tres maneras de sincronizar

1 · MISMA MÁQUINA — sqlite, instantáneo

N agentes y el studio comparten .taskops/db.sqlite (WAL: los lectores nunca esperan a un escritor). El claim es un INSERT sobre una primary key — 50 threads compitiendo, exactamente 1 ganador, medido.

2 · ENTRE MÁQUINAS — git, sin servidor

taskops sync exporta a events.jsonl → commit → push. El otro lado hace pull y el hook post-merge importa + materializa + desbloquea, solo. IDs por hash de contenido: importar dos veces es un no-op, no hay conflictos posibles.

3 · AL BROWSER — SSE, en vivo

El studio sigue un cursor sobre la tabla de eventos (cada 0.5s) + el bus in-process para los writes propios. Un write desde CUALQUIER proceso llega al browser — probado con un intérprete separado escribiendo y el frame leído de un socket real.

   taskops sync = 4 pasos, en este orden, todos idempotentes:

   import ──▶ replay ──▶ unblock ──▶ export
   (log →     (eventos →  (re-deriva   (lo local
    cache)     tasks y     qué está     nuevo →
               deps)       pickable)    al log)

   import ANTES de export: importar puede cerrar una tarea de la que
   dependen otras — exportar primero publicaría un grafo ya viejo.
   replay es el paso que faltaba (bug real): los eventos llegaban y
   el board quedaba vacío. hoy cada evento `created` lleva el snapshot
   completo de la task, y engine/replay.py los convierte en filas.

  el board se mueve SOLO: sin botón de refresh, sin polling del browser.
  el punto verde late con cada evento. SSE y no WebSocket, a propósito:
  el canal solo empuja (todo write del browser es un POST normal), el
  engine es sync por invariante, SSE es stdlib y atraviesa nginx sin
  upgrade. el stream se recicla solo cada 5 min y EventSource reconecta
  por spec — así el bound de recursos es de diseño, no una apuesta al OS.

Configurar dos devs remotos y sus agentes

El escenario completo: Ana en su máquina, Berna en la suya, un repo compartido en GitHub, los agentes de cada una coordinándose por el log. Paso por paso, verificado — cada comando de acá corrió de verdad antes de escribirse.

PASO 1 — ana adopta taskops (UNA sola persona hace esto)

cd ~/proyecto                  # su clone del repo compartido
pip install taskops            # (o desde el checkout: pip install -e ~/taskops)
taskops init                   # crea .taskops/, hooks de git, toca .gitignore
taskops sync
git add .gitignore .taskops/events.jsonl
git commit -m "taskops: adopt the shared task list"
git push

El orden importa: init toca .gitignore, y si dos personas lo crean por separado en un repo que no lo tenía, git se niega a mergear. Una adopta, el resto hereda.

PASO 2 — berna se suma (y cualquier dev después)

git pull                       # trae .gitignore + events.jsonl
pip install taskops
taskops init                   # sus hooks + ADOPTA el log que ya está ahí:
                               #   "adopted 3 change(s) from the committed log"
taskops report board           # ← ve las tareas de ana, con specs y deps

PASO 3 — cada una conecta sus agentes (una vez por máquina)

claude mcp add taskops -- python3 -m taskops.transports.mcp
claude plugin install ~/taskops/plugin      # hooks + skills /taskops:*

# identidad por terminal, para que el board distinga a los agentes:
export TASKOPS_ACTOR="agent:ana/api-1"      # terminal 1 de ana
export TASKOPS_ACTOR="agent:ana/ui-1"       # terminal 2 de ana
export TASKOPS_ACTOR="agent:berna/w1"       # terminal de berna
# (sin la variable, se resuelve de git config user.email → dev:ana)

Las 5 tools MCP, y las instrucciones que todo agente recibe

El server MCP inyecta sus instrucciones en el initialize — es el único texto de taskops que toda sesión ve garantizado, así que lleva el modelo mental y las dos reglas duras, no una repetición de cada tool. El schema de cada tool se genera de los TypedDicts: un parámetro no puede existir en el wire sin existir en el dispatch.

taskops_next · reclamar trabajo. Devuelve spec + branch exacta + warning de colisión + tu inbox. Si no hay nada, dice POR QUÉ (todo bloqueado ≠ todo tomado ≠ terminado). El claim es un lease: cada llamada tuya lo renueva; si tu proceso muere, expira en 15 min y la tarea vuelve a la cola.
taskops_update · progreso, comment, handoff, cierre, y MENSAJERÍA (mentions). status=released devuelve la tarea con tu avance escrito — la jugada honesta al quedarte sin contexto. status=done exige un commit atado (o no_code + justificación).
taskops_ask · leer una tarea entera: spec, hilo, commits, qué la bloquea, a quién bloquea, y qué otras tareas tocan sus archivos. Con query en vez de task, busca en títulos y specs.
taskops_plan · una descomposición entera en UNA llamada: tasks + árbol + DAG. after acepta el índice 0-based de una entrada anterior del mismo batch. El spec se escribe para un agente FRESCO sin tu contexto.
taskops_report · board / standup / fleet. Generados, así que no pueden estar desactualizados ni adular a nadie.

Las dos reglas que el server impone en vez de sugerir: un commit debe salir de la branch de la tarea reclamada (el trailer se inyecta solo), y done exige evidencia. Esas dos son la razón por la que el board se puede creer sin leer el diff.
