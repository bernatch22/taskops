Los flujos, exactos

Cómo se crean las cards, cómo un agente invoca a otros y les asigna trabajo, cómo se levanta el UI, y cómo funciona el WebSocket. Todo lo de acá corrió de verdad antes de escribirse.

1 · Cómo se crean las cards

Hay tres formas, y son tres situaciones distintas.

A · MUCHAS de una vez — el caso normal

Le decís al agente "planeá esto" y llama taskops_plan una vez con la lista entera. Es batch por una razón: las dependencias. De a una no podés decir "esta va después de la anterior" porque no conocés su id hasta que existe. 

taskops_plan tasks=[
  {"title":"Tabla de tokens", "spec":"Migración + modelo. Listo cuando…", "files":["models/token.py"]},
  {"title":"Emitir en login",  "spec":"…", "after":[0]},          ← índice de la entrada anterior
  {"title":"Rotar al usar",    "spec":"…", "after":[1]}
]

B · UNA sola — lista de un elemento

taskops_plan tasks=[{"title":"Arreglar el timeout", "spec":"…"}]

C · ME TRABÉ, creo la card que me bloquea — una sola llamada

Un agente laburando en tk-A descubre que falta algo antes. Con blocks crea la card y deja su propia tarea esperándola, atómicamente. Antes eran dos llamadas y la que se perdía siempre era la arista. 

taskops_plan tasks=[{
  "title": "Migrar el schema de sesiones",
  "spec":  "Lo descubrí haciendo tk-A: sin esto el token no persiste.",
  "blocks": ["tk-A"]                    ← mi tarea actual pasa a esperar esta
}]

   ANTES                         DESPUÉS
   tk-A  ○ ready                 tk-A     · backlog  ↑1  ← esperando
                                 tk-nueva ○ ready        ← alguien la puede agarrar ya

2 · Un agente invoca otros y les asigna una card

taskops_dispatch lanza un Claude Code headless real por card, cada uno en su propio git worktree, cada uno con la card ya asignada. No abrís terminales: el planner descompone y dispara. 

   TU SESIÓN                          TASKOPS                        LOS WORKERS
   ─────────                          ───────                        ───────────
   "planeá el refactor"
        │
        ▼
   taskops_plan  ─────────▶  3 cards + su DAG
        │
   taskops_dispatch count=3 ──▶ por cada card, EN ESTE ORDEN:
        │                        1. assignee = agent:berna/w1
        │                           (ANTES de lanzar — si fuera después,
        │                            el worker podría agarrar otra cosa)
        │                        2. git worktree add .taskops/trees/tk-xxx
        │                           -b tk/tk-xxx/slug
        │                        3. claude -p "sos agent:berna/w1, reclamá
        │                             tk-xxx…"  --allowedTools …
        │                           con TASKOPS_ROOT=  ────────▶ ● w1 arranca
        │                                                       ────────▶ ● w2 arranca
        ▼                                                       ────────▶ ● w3 arranca
   # dispatched 3 worker(s)                                              │
   | worker          | task     | pid   | branch                  |      │ cada uno:
   | agent:berna/w1  | tk-d993a0| 39498 | tk/tk-d993a0/add-greet  |      │  taskops_next task=…
   | agent:berna/w2  | tk-04e4f4| 39507 | tk/tk-04e4f4/add-fare…  |      │  codea en SU worktree
                                                                         │  commitea en SU rama
   vos seguís laburando; son detached y te sobreviven                     │  taskops_update done
                                                                         ▼
   taskops report fleet   ◀────── qué están haciendo ahora ──────────  y mueren
un worktree por worker
Dos agentes editando un mismo working tree se pisan, y ningún lease arregla eso: un lease coordina quién es DUEÑO de una tarea, no de qué bytes hay en disco. Cada worker tiene su directorio y su rama, y se mergean por git como dos personas.
TASKOPS_ROOT — la línea que sostiene todo
El worktree no tiene .taskops/, así que sin esto cada worker resolvería un proyecto vacío dentro de su propio directorio y no coordinaría con nadie. UN board, N working trees.
assignee filtra, no ordena
Una card asignada es INVISIBLE para todo otro agente — ni la ve en la cola ni la puede pedir por id. Sin eso, "asignada" sería una etiqueta que cualquiera ignora.
límites, a propósito
3 workers por default, 12 de techo. Cada uno es un proceso con un modelo atrás, así que el que quiere veinte lo tiene que pedir. Tools por allowlist, sin red (ni WebFetch ni WebSearch).
si un worker muere
Su lease vence y la card vuelve a la cola. Nada queda colgado, y no hay que limpiar nada a mano.

Dos bugs que encontró este flujo corriendo de verdad, invisibles a la revisión: un worker sin identidad en el prompt se inventó una (agent:claude/worker) y reclamó una card de otro — porque pedir por id nunca pasaba por el filtro de asignación. Los dos están arreglados y pineados por tests.

3 · Cómo se levanta el UI, y dónde se registran los proyectos

se levanta así, desde el repo

cd ~/mi-repo
taskops ui                       # → http://127.0.0.1:2140/
taskops ui --port 3000
taskops ui --readonly            # para una pantalla en la pared
taskops ui --host 0.0.0.0 --token "$(openssl rand -hex 16)"

los proyectos NO se registran en ningún lado

Y eso es una decisión, no un olvido. Una UI = un repositorio. No hay registry global, no hay lista de proyectos, no hay base de datos central. El estado vive dentro del repo (.taskops/), así que el proyecto es el directorio: cd y levantás. Dos proyectos = dos UIs en dos puertos. 

~/proyecto-a/.taskops/  ──▶  taskops ui --port 2140
~/proyecto-b/.taskops/  ──▶  taskops ui --port 2141

la búsqueda: el comando camina hacia ARRIBA buscando .taskops/, igual que git con .git
así que funciona desde cualquier subdirectorio. $TASKOPS_ROOT lo pisa (es lo que
usan los workers dispatchados desde su worktree).

El multi-proyecto con usuarios e invitaciones que querés en bernardocastro.dev es otra cosa y no existe todavía: necesita un registry, cuentas y permisos, o sea un servidor con estado propio. Hoy taskops es deliberadamente local.

4 · Cómo funciona el WebSocket

   BROWSER                       SERVER (threaded, sin asyncio)          SQLITE
   ───────                       ──────────────────────────────          ──────
   new WebSocket("/api/live")
        │  Upgrade: websocket
        ▼
   ┌─────────────────────┐   handshake: sha1(key + GUID) en base64
   │ 101 Switching        │◀── un thread por conexión, parado en un generador
   └─────────────────────┘
        │
        │◀── {"type":"hello"}          ← al instante; el UI refetchea el board
        │
        │                          usecases.follow() ──▶ polea un CURSOR
        │                                                events.after_seq()
        │                                                cada 0.5s        │
        │                                                     ▲          │
        │                          + bus in-process ───────────┘          │
        │                            (para los writes propios,            │
        │                             que así aparecen ya)                │
        │                                                                 │
        │                       ┌── otro agente escribe ──────────────────┤
        │◀── {"type":"change",  │   (OTRO PROCESO: cada agente MCP        │
        │     "event":{…}}      │    es su propio proceso)                │
        │                                                                 │
        │◀── PING cada 2s en silencio  ← el probe del protocolo, se contesta
        │
        │◀── close a los 5 min → EventSource/WS reconecta solo, y el UI
        │                        refetchea en cada open

   POR QUÉ POLEA UN CURSOR y no sólo escucha el bus: cada agente es un PROCESO
   distinto (MCP es stdio, cada hook de git es un intérprete nuevo). Un bus
   in-process no ve ninguno. El cursor sí — es un scan sobre un entero indexado.

   POR QUÉ 5 MIN DE VIDA: medido. Los writes a un socket local cerrado siguen
   funcionando +7 segundos, así que "detectar que el cliente se fue" no es
   confiable. Cerrar solo invierte el problema: el bound es de diseño.
WS a mano, sin dependencias
La librería websockets es asyncio, y el engine es sync por invariante testeada. Metería un event loop, un puente de threadpool y un segundo modelo de concurrencia. El framing de RFC 6455 que esto necesita son ~100 líneas (_wsframes.py) y deja el paquete en CERO dependencias.
SSE sigue ahí como fallback
Misma ruta, mismo feed, otro sobre. Si el upgrade no pasa (un proxy que lo mastica), el UI cae a SSE solo. Y hace que curl -N /api/live sea una herramienta de debug que funciona.
el browser sólo escucha
Todo lo que el UI escribe es un POST normal (un comment, un cambio de status). Por eso el canal es unidireccional y por eso el fallback a SSE no pierde nada.
